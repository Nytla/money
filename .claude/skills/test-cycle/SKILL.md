# Регламент тестирования money.com

Девять этапов из `docs/testing-cycle.xlsx`. Если в аргументах указан номер — выполнить
только этот этап. Иначе идти по порядку и **останавливаться на первом упавшем**: смысл
регламента в том, что дефект дешевле поймать на раннем этапе.

Итог оформить таблицей «этап → статус → что сломалось».

## 1. Статический анализ и линтинг

```
npm run format:check
npm run lint
npm run typecheck
```

Падение `format:check` чинится `npm run format` — это не дефект, а расхождение форматирования.
Ошибки типов и линта чинить по существу, не глушить `eslint-disable` и `any`.

## 2. Модульное тестирование

```
npm test
```

Проверить, что новая бизнес-логика покрыта. Приоритет покрытия: расчёт остатка,
десятина, агрегация по периоду, разбор и форматирование сумм и дат.
Покрытие смотреть через `npm run test:coverage`.

## 3. Интеграционное тестирование

Те же `npm test` — интеграционные тесты живут рядом с unit-овыми, но рендерят страницы
и формы через React Testing Library, а сетевые вызовы мокают через MSW.
Проверять: формы добавления операции, смену периода, работу с контекстом.

## 4. E2E

```
npm run test:e2e
```

Playwright сам поднимет дев-сервер. Критический сценарий: логин → добавление дохода →
добавление расхода → проверка остатка и десятины → экспорт в Excel → выход.

## 5. Производительность и Core Web Vitals

```
npm run build
npm run analyze
```

Смотреть размер First Load JS по маршрутам и отчёт анализатора бандла.
Recharts и таблицу подключать динамически, если они утяжеляют первый экран.
Lighthouse — вручную по собранному прод-билду (`npm run start`).

## 6. SEO и доступность

Проверка axe встроена в E2E (`tests/e2e/smoke.spec.ts`). При добавлении экрана —
добавить туда его проверку. Смотреть: ARIA у диалогов и таблицы, контрастность,
семантику разметки, работу с клавиатуры, метатеги в `layout.tsx`.

## 7. Безопасность

```
npm audit
```

Уязвимостей быть не должно. Кроме аудита проверить: заголовки безопасности из
`next.config.ts` реально отдаются; cookie сессии httpOnly + secure + sameSite;
все входные данные проходят через zod-схему; нет секретов в клиентском бандле
(переменные без префикса `NEXT_PUBLIC_`).

## 8. Нагрузочное тестирование

k6 — внешний бинарник, ставится отдельно (`winget install k6`). Гонять по
серверным действиям и API-роутам на прод-сборке. Актуально перед деплоем.

## 9. UAT

Ручная проверка по пунктам `docs/TZ.txt`: каждая кнопка и каждый столбец таблицы
из ТЗ должны существовать и работать. Результат — список расхождений с ТЗ.
