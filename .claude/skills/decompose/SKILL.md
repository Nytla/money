# Атомарная декомпозиция

Этот скилл отвечает **только за дробление** — на какие задачи распадается работа.
Порядок задач, фазы и зависимости во времени — дело [[plan-phase]], который берёт
результат этого скилла на вход. Требования приходят из [[prd]].

Вход: PRD или раздел ТЗ. Выход: файл `docs/tasks-<фича>.md` со списком задач.

## Что такое атомарная задача

Пять критериев. Задача атомарна, только если выполняются **все**.

**1. Вертикальный срез.** Задача даёт наблюдаемый результат, а не слой. Не «создать
таблицу операций» и отдельно «сделать форму», а «доход сохраняется и появляется
в журнале». Разнесение бэкенда и фронтенда по разным задачам даёт куски, которые
невозможно проверить по отдельности; в App Router с серверными действиями это
к тому же часто один файл.

Исключение — инфраструктура (миграция схемы, конфиг тестов). Такие задачи слоями
и являются, у них результат наблюдает разработчик, а не пользователь. Помечать их явно.

**2. Формулируется тест, который падает до и проходит после.** Если тест-кейс
не придумывается, задача либо слишком расплывчата, либо это не задача, а намерение.
Названия тест-кейсов пишутся прямо в задачу — они же станут основой тест-плана.

**3. Одна причина измениться.** Если формулировка содержит «и» — почти всегда две
задачи. «Добавить расход и посчитать остаток» — это «добавление расхода»
и «нарастающий остаток в журнале».

**4. Зависимости названы явно.** Что должно существовать до начала. Если список
зависимостей длиннее самой задачи — декомпозиция неверная, границу провели не там.

**5. Полдня–день работы.** Больше — дробить. Заметно меньше — скорее всего
это шаг внутри задачи, а не задача.

## Чего не делать

**Не дробить до бессмыслицы.** «Добавить поле в схему», «написать импорт»,
«создать файл» — это шаги реализации. Задача, у которой нет собственного критерия
готовности, отдельной задачей быть не должна.

**Не описывать реализацию.** Задача говорит, что должно стать правдой, а не как это
запрограммировать. Выбор структуры кода остаётся за исполнителем.

**Не изобретать объём.** Задач, которых нет в PRD, быть не должно. Если в процессе
дробления обнаружилось необходимое, но не описанное требование — не дописывать молча,
а вынести в раздел «Вопросы к PRD» и спросить.

## Формат задачи

```
### T-<номер>: <результат в одной строке>

**Тип:** пользовательская | инфраструктурная
**Зачем:** одна фраза о ценности; для инфраструктурных — что она разблокирует
**Зависит от:** T-<номера> или «ничего»
**Затрагивает:** зоны кода (журнал, категории, аутентификация, экспорт, статистика)

**Готово, когда:**
- [ ] проверяемое утверждение
- [ ] проверяемое утверждение

**Тест-кейсы:**
- unit: <название теста>
- интеграционный: <название теста>
- e2e: <название теста, если задача пользовательская>
```

Ссылка на источник обязательна: у каждой задачи — пункт PRD или ТЗ, из которого
она выведена. В конце файла — таблица покрытия: каждый критерий готовности из PRD
против задач, которые его закрывают. Непокрытый критерий означает пропущенную задачу.

## Специфика этого проекта

Задачи должны уважать конвенции из `AGENTS.md`, иначе критерии готовности окажутся
непроверяемыми:

- суммы в критериях — в минорных единицах либо с явным указанием формата;
- даты — календарным днём, без времени;
- каждая задача завершается зелёным `npm run verify`, это подразумевается
  и в критерии готовности не дублируется.

Уровни тестов брать из регламента `docs/testing-cycle.xlsx`: проверка 2 — модульные,
проверка 3 — интеграционные, проверка 4 — E2E. Пользовательская задача без e2e-кейса
и инфраструктурная без unit-кейса — повод перепроверить формулировку.

## Порядок работы

1. Прочитать PRD (или указанный раздел ТЗ) целиком.
2. Выписать все критерии готовности — это каркас будущего покрытия.
3. Разбить на задачи, каждую прогнать по пяти критериям выше.
4. Построить таблицу покрытия, найти дыры, дописать недостающие задачи.
5. Сохранить в `docs/tasks-<фича>.md` (имя латиницей, kebab-case).
6. Перечислить, что осталось неясным — вопросами, а не догадками.

Дальше результат уходит в [[plan-phase]] для расстановки по фазам.
